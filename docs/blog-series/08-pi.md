# Post 8 — Loop and graph engineering in Pi

**Thesis:** Pi has the smallest agentic surface of the three — and that's its advantage for scheduled work. It's the harness I trust with unattended jobs precisely because there's less to engineer around. Loops are shell; graphs are shell calling shell.

**Length:** ~1,100 words. **Sources:** your own machine (this is the most personal post; almost nothing about Pi's internals is published — say so, it's a differentiator).

⚠️ Verification note: Pi's public documentation is thin compared to Claude Code/OpenCode. Everything here is written from your working setup (`~/.pi/agent/`). Where you state internals, show the file. This post's credibility comes from receipts, not citations.

## What you get out of the box

- **Headless `pi -p`** — single non-interactive prompt execution; the atom every scheduled job is built from.
- **Extensions + skills system** — prompt-level packaging.
- **MCP adapter** — external tools scoped per config.
- **That's it.** No hooks, no SDK, no subagent tool, no server. The rest is Unix.

## Building the verifier loop (step-by-step)

1. Every job already funnels through one wrapper (`run-locked.sh`: atomic mkdir lock + logging). One edit instruments all of them — a genuine architectural win worth a paragraph.
2. The loop is pure shell: verifier → `pi -p` on failure → cap → exit code. Identical in shape to post 3's script.
3. launchd is the `/schedule` equivalent: local, free, vendor-independent, and survives reboots (unlike terminal-bound loops).

## Building the two-node graph (step-by-step)

1. Node one: `pi -p "author prompt" > draft.md`.
2. Node two: `pi -p "review $(cat draft.md) against: <bar>. Reply PASS or FAIL: reason" > verdict.txt` — fresh process = fresh context by construction.
3. Router: `grep -q "^PASS" verdict.txt || <re-run node one with critique>`.
4. This is bash, not a framework — and that's the point: for two nodes, the graph tax is three lines.

## Pros

- Smallest failure surface: no hook contract to misunderstand, no server to keep alive, no event stream to misread.
- Single-choke-point architecture (one wrapper for all jobs) made fleet-wide telemetry a one-file edit — the layer-audit system exists because of this.
- Fully vendor-independent scheduling (launchd/cron); loops keep running with no harness process alive at all.
- Forces the discipline this series teaches: with no magic available, you *must* write the verifier.

## Cons

- No in-band loop control: nothing like a Stop hook; all gating is external shell.
- No subagent/child-session primitive: "fresh context node" = new process, and context passing is manual (files, prompts).
- No structured-output channel: node verdicts are parsed from text (`grep ^PASS`), which is brittle at scale.
- Thin public docs: you're on your own for anything past the basics — every claim needs your own verification.
